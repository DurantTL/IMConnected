# AGENTS.md: IMConnected

Instructions for AI coding agents (Codex, Claude) working in this repo.

## Stack
- Astro 7 (`output: 'static'` + `@astrojs/node` standalone). Pages are prerendered, and only `src/pages/api/submit.ts`, `src/pages/api/publish.ts`, `src/pages/api/stories.ts` (`/api/stories`), `src/pages/api/studio-photo.ts` (`/api/studio-photo`), `src/pages/api/confirm.ts`, `GET /media/*` (`src/pages/media/[...path].ts`), the public story pages and feeds (`/`, `/stories/<slug>/`, `/<section>/`, `/<section>/<area>/`, `/stories.json`, `/rss.xml`; epic #25 step 2), `/images/stories/*` (only reached when the static file is missing), `/api/search` (epic #25 step 3), `/api/agent/*`, `/admin*` and `/api/admin/*` run on the server (`prerender = false`). `/submit/`, `/search/`, `/confirm/` and the 404 page are still prerendered.
- Content: `src/content/stories/*.md`, with the schema in `src/content.config.ts`.
- Search: SQLite FTS5 (`GET /api/search`, `src/pages/api/search.ts`; migration 013, `src/lib/search*.ts`). The query is reduced to quoted words and never passed to FTS5 as syntax; snippets are escaped before `<mark>` is added; results are only live, non-draft stories (the set `public-stories.ts` shows), and before the first mirror pass search falls back to an in-memory search over the build. No Pagefind. `/search/` is a prerendered page that calls the endpoint.
- Editor dashboard: `/admin*` and `/api/admin/*` are server-rendered and guarded by `src/middleware.ts` (session, 2FA state, Origin check, no-store/noindex headers). The middleware must return immediately for every other path: no database, cookies or session. The one exception is the in-memory page cache lookup for the few GET paths in `publicCacheKey()` (`src/lib/public-cache.ts`). See epic #7.
- Deploy: Docker image built by `.github/workflows/docker.yml` and pushed to GHCR.

## Rules
- Section and category definitions live only in `src/lib/site.ts`. If you change them, also update `.pages.yml`.
- When the content schema changes, keep `.pages.yml`, `src/lib/submission.ts` (frontmatter writer), `src/lib/feed.ts` (the `/stories.json` and `/rss.xml` feeds) and the README example in sync. Treat `/stories.json` fields as a public contract: add fields freely, but don't rename or remove one without bumping its `version`.
- Never render submitted text as raw HTML. `textToMarkdown()` in `src/lib/submission.ts` must keep escaping `< > & [ ]`.
- Submissions: `/api/submit` creates a `drafts` row (default `SUBMISSIONS_TO=dashboard`) and makes no GitHub call; `SUBMISSIONS_TO=github` is the old pull-request path, to be removed in a follow-up. If the database is down it answers 503 rather than lose the story. `/api/publish` (Studio) still commits straight to `main` and also records a `published` draft (source `studio`).
- AI agent API: `POST /api/agent/stories` (and `GET /api/agent/sections`) lets the communication director's AI agent send stories. Bearer `AGENT_API_TOKEN` (32+ characters, constant-time compare; 503 when unset or short), machine-to-machine, no CORS, not under `/api/admin`. It only ever creates a `new` draft (source `agent`) or updates one that is still `new` and untouched by an editor (idempotent by `sourceUrl`; otherwise 409), with the same escaping as dashboard drafts, `data:` photos only (never fetches a URL), 60 requests per hour. It cannot publish, reject or edit anything else. `GET /api/stories` is the authenticated list IMConnected Studio imports from (same `PUBLISH_TOKEN` and `PUBLISH_ORIGINS` as `/api/publish`); it never includes submitter contact details. `GET /api/studio-photo?src=` (`src/pages/api/studio-photo.ts`, same auth and CORS) returns the bytes of a story photo under `/images/stories/` or `/media/stories/` so Studio can upload it to WordPress; it never serves a draft's uploads.
- Storage: published stories stay Markdown files in git (publishing is a commit to `main`). A small SQLite database (`node:sqlite`, in `DATA_DIR`, a Docker volume at `/data`) holds editor accounts, sessions, drafts and the audit log, and (until step 4 of epic #25) a mirror of the published stories and their photo records. Schema changes are new numbered files in `src/lib/db/migrations/`; never edit an applied one. Don't add another datastore.
- Stories in the database (epic #25): migration 011 adds `stories` and `story_photos`. **Until step 4 the `stories` table is only a mirror of git**: `src/lib/story-sync.ts` refills it from the built content collection (baked into the server bundle, so it works in the image where the Markdown sources do not exist) on the first database open after a start, copying photos from `dist/client/images/stories/` into `DATA_DIR/media/stories/<slug>/<sha256>.<ext>`. It is idempotent, runs in the background inside try/catch (retried after about a minute on failure, at most 5 passes; no file I/O inside a write transaction; a photo is re-verified after a new build via a marker over the exact files the stories reference). Publishing and editing still go through git (the dashboard, Studio, Pages CMS or a commit) as before; do not write to `stories` by hand. The one write the dashboard makes to the table is unpublishing a story (with its hold, below). `GET /media/*` serves only `DATA_DIR/media` files that are jpg/png/webp, refuses traversal (encoded, double-encoded, backslash, absolute, symlinks), and the middleware does not touch it. Use `src/lib/story-store.ts` for access.
- Public pages from the database (epic #25, step 2 of 5): the home page, story, section and area pages, `/stories.json` and `/rss.xml` are rendered on the server through `src/lib/public-stories.ts`. **Fresh start rule:** the table is read only after the mirror has completed a pass in this process (`storySyncDone()`); before that, and whenever the table can't be read, pages are built from the built collection (what the prerendered pages used, minus slugs the dashboard unpublished), so a reader never sees a missing or empty page; the first public request starts the mirror, and completing it clears the cache. Rendered pages and feeds are cached in memory (`src/lib/public-cache.ts`: at most 300 entries, 10 minute TTL, keyed by `publicCacheKey()`, only 200 responses, a render that started before an invalidation is not stored); every `story-store.ts` write calls `invalidateStories()`, and so do the dashboard's unpublish (which also calls the store's `unpublishStory` and records a hold in `story_holds`, migration 012) and publish handlers, so an unpublished story is a 404 from this server at once (Cloudflare or a browser may keep the page they hold for up to about 6 minutes: `max-age=60` plus `stale-while-revalidate=300`). **Never revive an unpublished story with its old text:** the mirror and the build hold only its old text, so the dashboard's unpublish records a hold (`story_holds`, rule in `src/lib/story-holds.ts`, used by both the sync and the build fallback) with the UNPUBLISH commit sha (`out.sha` from `commitToBase`). Any image that contains that commit either leaves the story out (`draft: true`) or has text published after it by any path (dashboard, Studio, git, Pages CMS), so the hold ends when the running image's commit list contains it. The list is `/app/.build-commits` (`.github/workflows/docker.yml`: `git log -200 --format='%H %ct'`, copied by the Dockerfile; `BUILD_COMMITS_FILE` overrides it). Rule: no unpublish sha recorded: hidden; list contains it: released (the sync deletes the hold and the build's text goes live); list without it: hidden, except that a full 200-commit list whose oldest commit time is more than 10 minutes after the hold's `created_at` means the unpublish is older than the window and is in the build: released; no list (local or dev build): released only when the build marker is known and differs from the one at unpublish (a NULL marker never counts as different). The window check uses GitHub's own commit time (`commitToBase` returns the new commit's `committer.date`, stored as `unpublish_time`); no recorded time means no safeguard. A non-empty list with any malformed line or a duplicate sha is unusable and keeps every hold active; only an empty or whitespace-only file means "no list". The old sha-only list format is still accepted (no times, so no window safeguard). The unpublish handler writes the draft's unpublished state, the hold and the table row in ONE transaction right after the commit (the build marker is filled in afterwards); if that fails the editor is told not to publish before the next deploy. The publish handler refuses a draft that was unpublished (`unpublished_at` set) when no hold row exists, because the old text could come back; a released hold stays as a row with `released_at`, so publishing after a release is fine. Anything that can't be evaluated keeps held stories hidden. Responses carry `Cache-Control: public, max-age=60, stale-while-revalidate=300` (404s `no-store`). Until step 4 publishing still commits to git, so a newly published story reaches these pages only after the next image deploy (as before); do not move publishing off git here. Photo addresses on these pages are `/media/...`; `/images/stories/...` still works (static file, else a 301 to the `/media/` copy), because sent newsletters link to it. Keep the markup, URLs, SEO tags and the `/stories.json` shape and `version` unchanged.
- Backups (epic #25, issue #30): once `GDRIVE_SERVICE_ACCOUNT_JSON` (base64 key) and `GDRIVE_FOLDER_ID` are both set, the server backs itself up once a day after `BACKUP_HOUR` (UTC, default 9). Backups are off, with a clear status on `/admin/backups` (administrators only), when either is unset. `src/lib/backup.ts` is the scheduler (started at server start by `src/lib/backup-start.ts`, which a Vite plugin in `astro.config.mjs` imports into the Node adapter's server entry after `BACKUP_START_DELAY_MS`, default 30 s, doing nothing and never opening the database when Google is not configured; `getDb()` also calls it; one unref'd timer, runs claimed in `backup_runs` so a restart or a second process never doubles a backup; migration 014; at most 3 upload tries per file, then retried every 30 minutes reusing the day's finished local files; a permanent failure (400/401/403 not rate-limit/404) is flagged `permanent` and not retried that day) and the 48-hour email to active **administrators only** (once a day, existing email path; none when backups are simply not configured, where `/admin` shows admins a notice instead). The Drive folder must be inside a **Shared Drive** (service accounts have no My Drive quota) and its membership stays limited to the owner and the service account, because the backups hold personal data. The work is plain `.mjs` in `src/lib/db/` (the Docker image copies it for `scripts/restore-backup.mjs`): `backup-core.mjs` (names, retention: 7 newest days + 4 newest Sundays, the `VACUUM INTO` snapshot on its own connection in a worker thread (never stalls requests), a tar reader that verifies checksums, refuses stray pax headers and caps bytes (50 GB or free space) and entries (200,000), a minimal streamed tar.gz of `DATA_DIR/media` and `DATA_DIR/uploads`, a tar reader that only accepts regular files under those two folders), `gdrive.mjs` (service-account JWT signed with `node:crypto` RS256, scope `drive` by default (`GDRIVE_SCOPE=drive.file` opts in to the narrow one, which usually 404s on shared folders), token cached until expiry, resumable upload, list, delete) and `backup-run.mjs`. **Never log, store or render the key, a JWT or an access token**: every message goes through `redact()`. Drive deletes only touch files the account created whose names match `imconnected-YYYY-MM-DD.db` / `.media.tar.gz`. Tests use `scripts/mock-gdrive.mjs` (`GDRIVE_API_URL`, `GOOGLE_OAUTH_TOKEN_URL`) and a throwaway RSA key; never call real Google. The optional GitHub export of stories is not built (step 4 decides).
- Before finishing, run `npm run build`. It must pass with no errors.
- To test submissions: `node scripts/mock-github.mjs` plus `GITHUB_API_URL=http://localhost:4010`.

## Issues and Claude Code
- `codex-ready` marks an issue with acceptance criteria that an agent may build. `needs-decision` and `needs-human` mark issues blocked on a person and are never `codex-ready`.
- If a requirement is unclear and the answer would change behavior, stop, add the `needs-decision` label, and write down the question.
- Claude Code's subagents live in `.claude/agents/`; its routing rules are in `CLAUDE.md`.

## Data and human gates
- Use synthetic data only in sample stories, tests, screenshots and commits. Submitter contact details (email, phone) live only in the database and the editor-only panel in `/admin` (and in the PR description when `SUBMISSIONS_TO=github`); never copy them into story files, issues, logs, prompts, commits, or the emails sent to editors.
- Agents never connect to the production database or create real accounts; test against a throwaway `DATA_DIR` with synthetic data and delete it.
- The AI agent can only create `new` drafts, or update a draft that is still `new` and untouched, through `/api/agent/stories`. Publishing, rejecting and editing anything else stay a person's actions. Agents building this repo must never call the real `/api/agent/*` endpoints or use or ask for `AGENT_API_TOKEN`; test only against a local build with a made-up token.
- Only a person may publish or reject a draft in the dashboard (and merge or close a submission PR on the old `SUBMISSIONS_TO=github` path), merge any PR, deploy or pull a new image on the server, change the GitHub token or other secrets, or send a newsletter. Agents may prepare reviewable changes but must not cross those gates.
- The Studio "Publish to IMConnected" button (`/api/publish`) is a person's action. Agents must never call `/api/publish` against the real site, and must never use or ask for `PUBLISH_TOKEN` (the same token guards `GET /api/stories`). Test it only against `scripts/mock-github.mjs` with a made-up token.
- Only a person sets `GDRIVE_SERVICE_ACCOUNT_JSON` or `GDRIVE_FOLDER_ID` (the owner's Google key), or runs `scripts/restore-backup.mjs` against a real server's data. Agents never create a Google project or key, never ask for or use the real values, and test restores only into a throwaway `DATA_DIR`.
- Never log submitter email addresses or phone numbers (log the draft id or PR number instead). Editor notification emails carry only the escaped title and church plus a link. Agents must never send real email: test with `RESEND_API_KEY` unset, or point `EMAIL_API_URL` at a local mock of the Resend endpoint. Use only Cloudflare's documented Turnstile test keys, or `TURNSTILE_VERIFY_URL` pointing at a local mock.

## Editorial voice (for any sample or generated copy)
Warm but professional, faith-oriented without being overly formal, inverted-pyramid news style. Never invent names, events, quotes or facts about real people or churches.
