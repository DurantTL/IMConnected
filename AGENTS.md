Instructions for AI coding agents (Codex, Claude) working in this repo.

## Stack
- Astro 7 (`output: 'static'` + `@astrojs/node` standalone). Pages are prerendered, and only `src/pages/api/submit.ts`, `src/pages/api/publish.ts`, `src/pages/api/stories.ts` (`/api/stories`), `src/pages/api/studio-photo.ts` (`/api/studio-photo`), `src/pages/api/studio-draft-flyer.ts` (`/api/studio-draft-flyer`), `src/pages/api/confirm.ts`, `GET /media/*` (`src/pages/media/[...path].ts`), the public story pages and feeds (`/`, `/stories/<slug>/`, `/<section>/`, `/<section>/<area>/`, `/stories.json`, `/rss.xml`; epic #25 step 2), `/images/stories/*` (only reached when the static file is missing), `/api/search` (epic #25 step 3), `/api/agent/*`, `/admin*` and `/api/admin/*` run on the server (`prerender = false`). `/submit/`, `/search/`, `/confirm/` and the 404 page are still prerendered.
- Content: stories live in the SQLite database (`stories` and `story_photos`, photos in `DATA_DIR/media`), with the field set defined by `src/content.config.ts`. `src/content/stories/*.md` and `public/images/stories/` are a **frozen archive**: the server reads the built copy once, to adopt it (`src/lib/story-adopt.ts`), and never again.
- Search: SQLite FTS5 (`GET /api/search`, `src/pages/api/search.ts`; migration 013, `src/lib/search*.ts`). The query is reduced to quoted words and never passed to FTS5 as syntax; snippets are escaped before `<mark>` is added; results are only live, non-draft stories (the set `public-stories.ts` shows), and there is no fallback to the build: an unreadable index is `ok: false`. No Pagefind. `/search/` is a prerendered page that calls the endpoint.
- Search readiness (issue #38): every process checks that all live, non-draft stories have a matching index stamp before its first successful search. An incomplete initial index returns the existing `ok: false` response while background repair uses bounded 50-row batches, yields between batches and retries without waiting for writer locks. Missing/stale rows or a failed initial live row never count as completion. Once ready, retain the normal throttled repair, per-row failure tolerance and transactional story/index writes. Do not add an archive fallback or make unpublished/draft-only rows block public search readiness.
- Editor dashboard: `/admin*` and `/api/admin/*` are server-rendered and guarded by `src/middleware.ts` (session, 2FA state, Origin check, no-store/noindex headers). The middleware must return immediately for every other path: no database, cookies or session. The one exception is the in-memory page cache lookup for the few GET paths in `publicCacheKey()` (`src/lib/public-cache.ts`). See epic #7.
- Deploy: Docker image built by `.github/workflows/docker.yml` and pushed to GHCR. Stories are not committed, so content paths (`src/content/stories/**`, `public/images/stories/**`) do not trigger a build.

## Rules
- Multiple sections (migration024): `section` stays primary and owns `area`; `additionalSections` is a normalized list of central section keys. Omitted inputs preserve existing assignments for old editor/agent/Studio/import clients; explicit `[]` clears extras. Keep drafts, revisions, publication/reopen, adoption/import and additive version1 feeds in sync. Section discovery/counts/search match membership without duplicating a story; area filters require the matching primary section. `src/lib/site.ts` owns normalization and membership helpers. See `docs/MULTIPLE-SECTIONS.md`.
- Website navigation (migration 023) is a version-checked SQLite configuration edited only by administrators at `/admin/navigation`. `src/lib/site-navigation.ts` validates public root-relative/HTTPS links and derives defaults from `site.ts`; do not move section definitions into settings. Public `GET /api/navigation` returns visible links only, and prerendered headers refresh from it without opening the database during build. Menu saves audit counts/version, invalidate public caches and never write story rows. Homepage events use public stories only, upcoming dates by America/Chicago day and full-aspect flyers. The owner-requested seven-second auto-advance has persistent Pause/Resume controls, suspends on hover/focus/hidden tabs/offscreen, and is disabled for reduced motion; content stays readable without JavaScript. See `docs/COMMUNITY-NAVIGATION.md` and `docs/PUBLICATION-REDESIGN.md`.
- Section and category definitions live only in `src/lib/site.ts`. `.pages.yml` belongs to the frozen archive and no longer needs to follow.
- When the content schema changes, keep `src/content.config.ts`, `src/lib/photo-layouts.ts`, `src/lib/story-store.ts` and `src/lib/story-publish.ts` (the row writers), `scripts/import-git-stories.mjs`, `src/lib/feed.ts` (the `/stories.json` and `/rss.xml` feeds), the migrations and the README example in sync (`.pages.yml` is a frozen archive config). Treat `/stories.json` fields as a public contract: add fields freely, but don't rename or remove one without bumping its `version`.
- Photo layouts (issue #35): a story's `photoLayout` (`one` | `twoUp` | `heroGrid` | `mosaic` | `stack`, Studio's story layouts, default `one`) lives in `src/lib/photo-layouts.ts` (the only list of values and the `planPhotos()` rules), `stories.photo_layout` and `drafts.photo_layout` (migration 016), the editor's picker, `/api/publish` (validated, 400 on an unknown value, default `one`), the agent API (`bad_photo_layout`) and `/stories.json` (a new field, `version` unchanged). The layouts render through `src/components/StoryPhotos.astro` in plain CSS grid, never lose a photo, and have no per-photo captions (owner decision). The 2026 magazine redesign intentionally changed the public markup, so `one` is no longer byte-identical to the old pages and `scripts/test-public-pages.mjs`'s `BASELINE_DIR` comparisons do not apply to it (see `docs/DESIGN_REVIEW.md`). Click-to-enlarge is `src/scripts/photo-viewer.ts`: a native `<dialog>`, no dependency, every photo stays a link to the full image without JavaScript. Standalone `{{photo N}}` Markdown lines place a story-owned photo inline (1 = lead); `story-media-render.ts` resolves current ordered slots, keeps crop/viewer links and removes only those slots from the surrounding layout. Invalid markers warn in private preview and emit no public media. Marker-like prose and code stay literal; derived feed/search text strips marker syntax. Modules remain a separate editing mode.
- Story modules (migration 017, `src/lib/story-blocks.ts`, `story-block-render.ts`, `src/scripts/story-builder.ts`): an editor-only way to build a story from paragraph, heading, quote, list, image, button and divider modules, plus Gallery, Flyer, Video and one/two-column Section containers, stored as JSON in `drafts.story_blocks` / `stories.story_blocks` with a Markdown projection in `body` for search and older consumers. Module text is escaped like the body: every `<` becomes `&lt;` when a story is written (`escapeStoryBlocks()`, applied in `writeStory`, the import script and the feeds) and the renderer shows plain-text fields literally. An image module shows only the story's **own** photos (a `/media/stories/...` or `/images/stories/...` path that is one of its lead or gallery photos, or a draft photo by ID), never an external address; image modules add nothing to the Markdown projection. Use walkStoryBlocks/mapStoryBlocks and storyBlockPhotos/mapStoryPhotos for nested structures. Sections cannot nest; every section and child shares the global60-node limit. Modules together are limited to the same 20,000 characters as the body. Public readers only see the rendered modules; submitted stories, the AI agent API and Studio never create them.
- Announcements (migration019): nullable typed `announcement` JSON on drafts/stories; `announcement.ts` validates kind/eventDate/location/links/videoUrl. Agent omission preserves on untouched updates; null clears; human review/publish rules remain. First photo is an uncropped flyer in every placement; retain original bytes/crop metadata. Flyer modules use own draft photo IDs/public positions and Video modules use exact HTTPS YouTube/Vimeo IDs. Public players load only on explicit user action; private preview stays script-disabled and link-only. Keep editor settings, Studio omission/history, content/import/adoption and additive version1 feeds in sync. See docs/AGENT-ANNOUNCEMENTS.md.
- Photo crops (migration 018): `draft_photos.zoom` and `story_photos.zoom` default to 1, constrained to 1–3. Focal X/Y stay 0–100. Zoom and pan change display metadata only; keep original bytes and full-image viewer links. Missing fields in older forms preserve stored crop values. Keep publish/reopen, adoption/import, content schema, public photos, inline modules and additive feed metadata in sync. A zoomed image requires an overflow-clipping parent; its `object-position` and `transform-origin` use the same focal point.
- Draft revisions (migration 021): retain the latest 20 previous editorial states in SQLite, in the same transaction as each changed save/photo operation. Use the explicit whitelist in `draft-revisions.ts`; never include contacts, source URLs, agent notes, upload paths or account/session secrets. Restore is version-checked and editable-draft-only, records the current state plus audit atomically, and never publishes or resurrects files. Match photos by stable `draft_photos.media_key`, never a reusable integer ID; remove missing module references and remap only executable Markdown markers through the Markdown AST. Keep code/link/escaped examples inert. Missing-media warnings must remain visible after reload.
- Never render submitted text as raw HTML. `textToMarkdown()` in `src/lib/submission.ts` must keep escaping `< > & [ ]`.
- Submissions: `/api/submit` creates a `drafts` row and makes no GitHub call. If the database is down it answers 503 rather than lose the story. The old `SUBMISSIONS_TO=github` pull-request path was removed in epic #25 step 4 (a merged submission PR would add a Markdown file the site no longer reads). **Nothing in the app calls GitHub any more**; `src/lib/github.ts` and `scripts/mock-github.mjs` are gone, and `GITHUB_TOKEN`, `GITHUB_REPO`, `GITHUB_BASE_BRANCH`, `GITHUB_PR_LABEL` and `SUBMISSIONS_TO` are not read. `/api/publish` (Studio) writes to the database in one transaction and also records a `published` draft (source `studio`); its response keeps a `commit` key that is always `null`.
- AI agent API: `POST /api/agent/stories` (and `GET /api/agent/sections`) lets the communication director's AI agent send stories. Bearer `AGENT_API_TOKEN` (32+ characters, constant-time compare; 503 when unset or short), machine-to-machine, no CORS, not under `/api/admin`. The original submission endpoint creates a `new` draft (source `agent`) or updates one still `new` and untouched by an editor (idempotent by `sourceUrl`; otherwise 409). Explicit `POST /api/agent/stories/reopen` may copy any currently public story/announcement/event into an In review draft, apply partial changes and append validated data photos. Preserve omitted fields verbatim, modules and original photo/crop order; reject body replacement on module stories. Never overwrite an open/rejected draft or write live story state. Eligibility, draft/photo changes, hashed requestId/payload receipt and audit must share one transaction; failed uploads roll back and old uploads are removed only after commit. Identical retries acknowledge without mutation, even after editor changes. See docs/AGENT-REOPEN.md. All agent routes share the 60/hour limit and escaping/photo validation; the agent cannot publish, unpublish, reject, read private drafts/uploads or reach admin routes. Human review/publication remains required. `GET /api/stories` is the authenticated list IMConnected Studio imports from (same `PUBLISH_TOKEN` and `PUBLISH_ORIGINS` as `/api/publish`); it never includes submitter contact details. `GET /api/studio-photo?src=` (`src/pages/api/studio-photo.ts`, same auth and CORS) returns a story photo so Studio can copy it to WordPress; it never serves a draft's uploads. Separately, `/api/studio-draft-flyer` uses the Studio token to copy only an open typed announcement's current lead upload. Bind its descriptor to draft/photo/media_key, recheck status/order/identity on every read, never return paths or contacts, and keep ordinary draft uploads inaccessible. This is a Studio-only copy capability; the AI agent cannot read flyers through it.
- Storage: **stories live in SQLite** (epic #25 step 4), not in git. A small SQLite database (`node:sqlite`, in `DATA_DIR`, a Docker volume at `/data`) holds editor accounts, sessions, drafts, the audit log, the published stories (`stories`, `story_photos`, `stories_fts`) and `app_state` flags; photos are files under `DATA_DIR/media/stories/<slug>/<sha256>.<ext>`. That file and folder are the **only copy**, so the nightly backup matters (the publish screen and the dashboard home remind administrators when backups are off; publishing is never blocked on it). Schema changes are new numbered files in `src/lib/db/migrations/`; never edit an applied one. Don't add another datastore. Use `src/lib/story-store.ts` for access and `src/lib/story-publish.ts` for publishing.
- Publishing to the database (epic #25 step 4): dashboard Publish, Publish changes, Unpublish, the edit-a-live-story flow and Studio's `/api/publish` write `stories` / `story_photos` (and the draft row and search entry) in **one transaction**, after copying the photos into `DATA_DIR/media` (content-addressed; files created by a failed attempt are deleted), then call `invalidateStories()`. A story is live in the pages, feeds, search and `/api/stories` on the very next request; there is no commit, build or deploy. The draft version check, the slug reservation (unique indexes on `stories.slug` and `drafts.slug`, no `await` between the slug check and the writes), the audit entries (`draft.publish`, `draft.unpublish`, `draft.published_studio`, `draft.studio_overwrote_live`) and the human gates are unchanged. `drafts.published_commit` holds the marker `db` for a story published this way (the column predates the move). `stories.edited_at` is set by a person's dashboard or Studio change and makes `scripts/import-git-stories.mjs` leave the story alone unless `--force`. Never write to `stories` by hand outside migrations, the import script and tests.
- One-time adoption (`src/lib/story-adopt.ts`, replaces the step 1 mirror and the step 2 holds): the first start of this version on a database without `app_state.git_adopted_at` imports the built content collection (what a deployed older image mirrored), shaped like the old mirror pass: a missing or older git-sourced story is imported and its photos copied, a story the dashboard unpublished or whose `story_holds` hold is still active stays unpublished, a git story gone from the build is unpublished, and a row whose source is not `git` is never touched. The flag is set (and remaining holds released) in one transaction only when no story failed; retries are 5 passes per process. From then on the build is never read for content, so a redeploy or an older image can never revert an edit. `story_holds` (migration 012, renamed `story_holds_retired` by 015), `src/lib/story-holds.ts` and `/app/.build-commits` (`docker.yml`, Dockerfile) are used only by that one pass and are inert afterwards; remove them with a migration that drops the table once every server has adopted. Everything the pass decides on is re-read inside its per-story write transaction (row still git-sourced, `updated_at` unchanged, `edited_at` not newer than migration 015's `applied_at`), so a concurrent publish, edit or unpublish is never overwritten. **Old-image guard:** `stories.rev` is bumped by every write of step-4 code (`writeStory`, `unpublishStory`, the import script, the adoption), and a trigger (active from migration 015 on) refuses any `UPDATE` that does not bump it, so a future migration that `UPDATE`s `stories` must set `rev = rev + 1` or it aborts; with the renamed holds table this stops a pre-step-4 image's mirror from reverting or unpublishing rows. Any code or test that updates `stories` directly must set `rev = rev + 1`.
- Public pages from the database (epic #25): the home page, story, section and area pages, `/stories.json` and `/rss.xml` are rendered on the server through `src/lib/public-stories.ts` from the table only. **There is no build fallback**: an empty table is a real empty site (on a brand new database the first request or search waits up to 60 s for the adoption), and if the table can't be read the pages, feeds and `/api/stories` answer `503` (`no-store`) and search says it is unavailable (`StoriesUnavailable`, `unavailableResponse`). Rendered pages and feeds are cached in memory (`src/lib/public-cache.ts`: at most 300 entries, 10 minute TTL, keyed by `publicCacheKey()`, only 200 responses, a render that started before an invalidation is not stored); every publish, unpublish and `story-store.ts` write calls `invalidateStories()`. Cloudflare or a browser may keep a page for up to about 6 minutes (`max-age=60` plus `stale-while-revalidate=300`; 404s `no-store`). `GET /media/*` serves only `DATA_DIR/media` files that are jpg/png/webp, refuses traversal (encoded, double-encoded, backslash, absolute, symlinks), and the middleware does not touch it. Photo addresses on pages are `/media/...`; `/images/stories/...` still works (the static archive file, else a 301 to the story's `/media/` copy) because sent newsletters link to it. Keep the URLs, SEO tags, feeds and the `/stories.json` shape and `version` unchanged. (The page markup itself was intentionally redesigned in 2026; see `docs/DESIGN_REVIEW.md`.)
- Importing stories committed by hand: `scripts/import-git-stories.mjs` (dry run unless `--apply`; never overwrites a story whose `source` is not `git` or whose `edited_at` is set unless `--force`; validates sections, areas and photos). Agents run it only against a throwaway `DATA_DIR` with synthetic stories (`scripts/test-import-git-stories.mjs`).
- Backups (epic #25, issue #30): once `GDRIVE_SERVICE_ACCOUNT_JSON` (base64 key) and `GDRIVE_FOLDER_ID` are both set, the server backs itself up once a day after `BACKUP_HOUR` (UTC, default 9). Backups are off, with a clear status on `/admin/backups` (administrators only), when either is unset. `src/lib/backup.ts` is the scheduler (started at server start by `src/lib/backup-start.ts`, which a Vite plugin in `astro.config.mjs` imports into the Node adapter's server entry after `BACKUP_START_DELAY_MS`, default 30 s, doing nothing and never opening the database when Google is not configured; `getDb()` also calls it; one unref'd timer, runs claimed in `backup_runs` so a restart or a second process never doubles a backup; migration 014; at most 3 upload tries per file, then retried every 30 minutes reusing the day's finished local files; a permanent failure (400/401/403 not rate-limit/404) is flagged `permanent` and not retried that day) and the 48-hour email to active **administrators only** (once a day, existing email path; none when backups are simply not configured, where `/admin` shows admins a notice instead). The Drive folder must be inside a **Shared Drive** (service accounts have no My Drive quota) and its membership stays limited to the owner and the service account, because the backups hold personal data. The work is plain `.mjs` in `src/lib/db/` (the Docker image copies it for `scripts/restore-backup.mjs`): `backup-core.mjs` (names, retention: 7 newest days + 4 newest Sundays, the `VACUUM INTO` snapshot on its own connection in a worker thread (never stalls requests), a tar reader that verifies checksums, refuses stray pax headers and caps bytes (50 GB or free space) and entries (200,000), a minimal streamed tar.gz of `DATA_DIR/media` and `DATA_DIR/uploads`, a tar reader that only accepts regular files under those two folders), `gdrive.mjs` (service-account JWT signed with `node:crypto` RS256, scope `drive` by default (`GDRIVE_SCOPE=drive.file` opts in to the narrow one, which usually 404s on shared folders), token cached until expiry, resumable upload, list, delete) and `backup-run.mjs`. **Never log, store or render the key, a JWT or an access token**: every message goes through `redact()`. Drive deletes only touch files the account created whose names match `imconnected-YYYY-MM-DD.db` / `.media.tar.gz`. Tests use `scripts/mock-gdrive.mjs` (`GDRIVE_API_URL`, `GOOGLE_OAUTH_TOKEN_URL`) and a throwaway RSA key; never call real Google. The database is the only copy of the stories, so backups are the safety net; there is no GitHub export.
- Before finishing, run `npm run build`. It must pass with no errors.
- To test submissions, publishing and Studio: the end-to-end scripts under `scripts/test-*.mjs` start the built server against a throwaway `DATA_DIR` (`test-editor-submissions.mjs`, `test-editor-drafts.mjs`, `test-public-pages.mjs`, `test-story-store.mjs`, `test-search.mjs`, `test-import-git-stories.mjs`); no GitHub token or mock is involved.

## Issues and Claude Code
- `codex-ready` marks an issue with acceptance criteria that an agent may build. `needs-decision` and `needs-human` mark issues blocked on a person and are never `codex-ready`.
- If a requirement is unclear and the answer would change behavior, stop, add the `needs-decision` label, and write down the question.
- Claude Code's subagents live in `.claude/agents/`; its routing rules are in `CLAUDE.md`.

## Data and human gates
- Use synthetic data only in sample stories, tests, screenshots and commits. Submitter contact details (email, phone) live only in the database and the editor-only panel in `/admin` ; never copy them into story rows, issues, logs, prompts, commits, or the emails sent to editors.
- Agents never connect to the production database or create real accounts; test against a throwaway `DATA_DIR` with synthetic data and delete it.
- The AI agent can only create `new` drafts, or update a draft that is still `new` and untouched, through `/api/agent/stories`. Publishing, rejecting and editing anything else stay a person's actions. Agents building this repo must never call the real `/api/agent/*` endpoints or use or ask for `AGENT_API_TOKEN`; test only against a local build with a made-up token.
- Only a person may publish, unpublish or reject a draft in the dashboard, merge any PR, deploy or pull a new image on the server, change secrets, run `scripts/import-git-stories.mjs --apply` or restore a backup against a real server's data, or send a newsletter. Agents may prepare reviewable changes but must not cross those gates.
- The Studio "Publish to IMConnected" button (`/api/publish`) is a person's action. Agents must never call `/api/publish` against the real site (it now publishes instantly and irreversibly to the live database), and must never use or ask for `PUBLISH_TOKEN` (the same token guards `GET /api/stories`). Test it only against a local build with a throwaway `DATA_DIR` and a made-up token.
- Only a person sets `GDRIVE_SERVICE_ACCOUNT_JSON` or `GDRIVE_FOLDER_ID` (the owner's Google key), or runs `scripts/restore-backup.mjs` against a real server's data. Agents never create a Google project or key, never ask for or use the real values, and test restores only into a throwaway `DATA_DIR`.
- Never log submitter email addresses or phone numbers (log the draft id or PR number instead). Editor notification emails carry only the escaped title and church plus a link. Agents must never send real email: test with `RESEND_API_KEY` unset, or point `EMAIL_API_URL` at a local mock of the Resend endpoint. Use only Cloudflare's documented Turnstile test keys, or `TURNSTILE_VERIFY_URL` pointing at a local mock.

## Editorial voice (for any sample or generated copy)
Warm but professional, faith-oriented without being overly formal, inverted-pyramid news style. Never invent names, events, quotes or facts about real people or churches.
