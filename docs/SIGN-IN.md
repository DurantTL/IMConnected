# Editor sign-in, two-step verification and recovery


- **`AUTH_SECRET`** (32+ random characters, in `.env`) is required. It encrypts stored authenticator secrets (AES-256-GCM) and keys the recovery-code hashes. Without it every `/admin` URL answers 503. Don't change it once editors have enrolled, or their authenticators stop working and they need new invites.
- **Accepting an invite.** The link opens "set your password" (12-256 characters, not the email address, not a common password; hashed with scrypt, N=2^15). The editor then scans a QR code (or types the key) into an authenticator app, confirms with one code, and gets **10 single-use recovery codes**, shown once; only keyed hashes are stored.
- **Signing in** is two steps: `/admin/login` (email + password), then `/admin/2fa` (6-digit code, a recovery code, or a passkey). A session that hasn't finished both can only reach the 2FA pages and sign-out. Each step issues a new session id.
- **Passkeys (WebAuthn).** Uses `@simplewebauthn/server` and `@simplewebauthn/browser` (exact versions pinned; the browser part is bundled by Astro and served from this site, no CDN). The relying party comes from **`SITE_URL`**: RP ID = its hostname, expected origin = its origin, never the request. Without a valid `SITE_URL` (https, or `localhost`) passkey buttons are hidden and passkey endpoints answer 503. Don't change the `SITE_URL` hostname once editors have passkeys, or they stop working.
  - *Enrollment:* "Use a passkey instead of an authenticator app" on `/admin/2fa/setup`. A passkey counts as a confirmed second factor, and the first factor generates the 10 recovery codes.
  - *Sign in:* "Sign in with a passkey" on `/admin/login` (discoverable credential, user verification required) satisfies both factors and starts a full session. After a password, `/admin/2fa` also offers "Use a passkey" next to the code field.
  - *My account:* "Linked sign-in accounts" lists each linked provider with **Unlink**, and a **Link Google account** / **Link Microsoft 365 account** button for each configured provider that is not linked yet. Linking is how an existing (active) editor adds a provider: it needs a fresh authenticator or recovery code (or passkey) and starts a flow whose signed cookie is bound to that editor's user id, the session that started it (a hash of the session id, never the token) and the provider; the callback links the provider's account only for the same fully signed-in editor in that same session (another session, even the same editor signed in again, another editor, a half-signed-in session or nobody is refused; refused attempts by a signed-in editor don't count toward the IP lockout), refuses an account that is already linked to anyone, never changes the session, is audited (`auth.oauth_linked`, actor, via account) and returns to My account. The provider's email need not equal the account email. Unlinking needs a fresh factor and is refused when it would leave no first-factor method (no password, no passkey and no other provider). An editor who joined with Google or Microsoft has no password, so My account offers **Set a password** (the usual password rules, a fresh second factor, other sessions signed out, audited).
  - *Safety:* challenges are stored in `webauthn_challenges`, single use, valid 5 minutes. A signature counter that doesn't go forward (when either value is non-zero) is refused and audited. Passkey sign-in shares the password step's rate limits (10 failures per IP, 5 per account in 15 minutes). Registrations, removals, renames, sign-ins and failures are in the audit log.
- **Google and Microsoft 365 sign-in (invite-only, issue #11).** Optional buttons on `/admin/login`. They only ever replace the password step: an OAuth sign-in starts a session that still needs the second factor (`/admin/2fa`, or enrollment), and nobody can sign up this way. A person sets this up once; agents never create the apps or use real secrets. A provider's button shows only when its variables are set (the build passes with or without them), and `SITE_URL` must be the public address, because the redirect URIs come from it, never from the request. No OAuth library is used: the flow is `node:crypto` and `fetch` only (`src/lib/auth/oauth.ts`; the claim rules are in `src/lib/auth/oauth-claims.mjs`).
  - *Who can sign in:* only (1) an account already **linked** in `oauth_accounts` (matched by the provider's stable subject, so a changed email changes nothing), or (2) a person who is **invited**: an `invited` editor whose invite is still unused and unexpired and whose email equals the provider's **verified** email. The second case links the account, activates the editor, uses up the emailed invite link and goes to authenticator enrollment; it is the only place an email is matched. An **active** editor with no link for that provider is rejected (so an administrator's unlink, or a two-step reset, can't be undone by signing in again), and so is an expired or revoked invite: they all see "This account isn't set up for IMConnected. Ask an admin for an invite" and nothing is created. Disabled editors never match. An editor links one account per provider. **Administrators: invite the editor's exact work address** (the one the provider will report).
  - *Claims:* every ID token must have our client id as audience, an unexpired `exp`, the `nonce` from the sign-in cookie and the provider's issuer (Google: `https://accounts.google.com`; Microsoft: `https://login.microsoftonline.com/<tenant>/v2.0`). Google also needs `email_verified=true`. **Microsoft is single-tenant only:** it is switched on only when `MICROSOFT_TENANT_ID` is the conference's tenant (directory) id, a GUID. `organizations`, `common`, `consumers` or an empty value turn the Microsoft button off (one note is logged at startup), because the `email` claim from another tenant is not proof that the person owns that address. `tid` must equal the configured tenant (the personal-account tenant is refused too) and the address is `email`, else `preferred_username`, from that tenant. *Accepted residual risk:* inside the conference's own tenant the address is whatever that tenant says (a guest account, or a mis-set `mail` attribute, could report an address that isn't the person's); that is why the address only ever matters for accepting an invite, and linking an existing editor is done by that editor from My account. The ID token is read from the token endpoint's response over TLS, so its signature is not re-checked (OpenID Connect Core 3.1.3.7).
  - *Flow safety:* `/admin/oauth/<provider>` (a signed-in editor who has passed 2FA is just sent to `/admin`) stores `state`, the PKCE verifier and a nonce in a 10-minute `__Host-imc_oauth` cookie (HttpOnly, Secure, SameSite=Lax, single use) that is **signed**: the value is `<base64url JSON>.<base64url HMAC-SHA256>`, keyed by an HKDF subkey of `AUTH_SECRET` (`signToken`/`verifyToken` in `src/lib/auth/secret.ts`), checked in constant time before the JSON is parsed, so an unsigned, altered or wrongly-signed cookie is treated exactly like a missing one (nothing counted, nothing audited) and redirects with `response_type=code`, PKCE S256, scope `openid email profile` and `prompt=select_account`. The callback checks the state in constant time, then POSTs the code, the PKCE verifier and the redirect URI to the provider's token endpoint with the client id and secret in the form body (`client_secret_post`, which Google and Entra both accept; there is no Basic header, and neither goes in a URL), no redirects, a 10-second limit for the whole response and a 100 KB cap counted on the decoded bytes (a compressed response can't get past it). It rejects anything wrong with one fixed message (nothing from the provider or the URL is shown). A callback without a valid state (no cookie, wrong state or provider) is not counted and not audited, because anyone can forge one cross-site; failures after a valid state count against the same per-IP lockout as password sign-in (10 in 15 minutes) and a locked IP writes no audit row per request. Starts are limited to 30 per IP in 15 minutes. Links, sign-ins, unlinks and failures are in the audit log by reason code only: never a token, code, secret or a stranger's address.
  - *My account:* "Linked sign-in accounts" lists each provider with **Unlink**. Unlinking needs a fresh authenticator or recovery code (or passkey) and is refused when it would leave no first-factor method (no password, no passkey and no other provider). An editor who joined with Google or Microsoft has no password, so My account offers **Set a password** (the usual password rules, a fresh second factor, other sessions signed out, audited).
  - *Administrators:* `/admin/editors` shows each editor's linked providers (provider, date and the address they linked, no tokens) with an **Unlink** action (an administrator's POST, Origin-checked, with the same fresh-factor confirmation as the other account actions, audited as `auth.oauth_unlinked` with the actor and the number of sessions revoked). Unlinking also signs that editor out everywhere, in the same transaction. **Reset two-step sign-in** (and `scripts/reset-2fa.mjs`) also removes that editor's linked Google and Microsoft accounts in the same transaction, An editor who has no password (they joined with Google or Microsoft) would then have no first factor left, so the reset also puts them back to **Invited** (name, role and audit history stay; old invite rows are removed; the audit entry says `reinvite: true`): the page says so, and an administrator uses **Send a new invite** (Manage), after which accepting it through the invite link, Google or Microsoft works as for a new editor. An editor who has a password stays active and goes to enrollment at the next sign-in. `users.activated_at` (migration 039) remembers that an account was ever active: **Revoke invite** deletes only a never-activated invite; for a person who was active it removes the invites and sets the account to **disabled** (audited `disabled: true`), never deletes it, because deleting would detach their drafts, revisions and audit history (and let the agent overwrite a draft a person touched). Re-enabling a disabled editor who has no password, link or passkey brings them back as Invited.
  - *Set up Google (one time):* in [Google Cloud Console](https://console.cloud.google.com/) create or choose a project, then **APIs & Services > OAuth consent screen**: user type **Internal** if the conference uses Google Workspace (otherwise External, in production), app name "IMConnected editors", scopes `openid`, `email`, `profile`. **Credentials > Create credentials > OAuth client ID**, type **Web application**, authorized redirect URI exactly `https://<your-site>/admin/oauth/google/callback` (no trailing slash; the host must equal `SITE_URL`). Put the client id and secret in `.env` as `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` and restart.
  - *Set up Microsoft 365 (one time, single tenant):* in the [Entra admin center](https://entra.microsoft.com/) go to **App registrations > New registration**: name "IMConnected editors", supported account types **Accounts in this organizational directory only** (single tenant), redirect URI platform **Web** with exactly `https://<your-site>/admin/oauth/microsoft/callback`. On the app's Overview copy **Application (client) ID** and **Directory (tenant) ID**. **Certificates & secrets > New client secret**, copy the *value* now. **API permissions**: Microsoft Graph delegated `openid`, `email`, `profile` (no admin consent is needed for them). Optional claims: add the `email` ID-token claim. In `.env` set `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` and **`MICROSOFT_TENANT_ID=<the directory (tenant) id>`** (required: without a GUID the Microsoft button stays off), then restart.
  - *Testing:* `npm run build`, then `DATA_DIR=/tmp/imc-oauth node scripts/test-editor-oauth.mjs`. It starts the committed `scripts/mock-oidc.mjs` (a local stand-in for both providers) and three built servers itself, with made-up client ids and secrets, and also checks the claim rules against the real issuers. The `OAUTH_GOOGLE_AUTH_URL`, `OAUTH_GOOGLE_TOKEN_URL`, `OAUTH_GOOGLE_ISSUER` and Microsoft equivalents exist for that test only. Under `NODE_ENV=production` they are ignored unless `OAUTH_TEST_ENDPOINTS=1` is also set, and each must be https or http on localhost: **never set any of these on a real site.** The server logs a warning at startup when they are set under `NODE_ENV=production`.
- **Errors and limits.** An unknown email, a wrong password and a disabled account all show "Email or password is incorrect." and cost the same time. 10 failures per IP or 5 per account in 15 minutes lock sign-in for that IP or account (the same message either way). Recovery-code use, failures, password changes and session revocations are in the audit log.
- **My account** (`/admin/account`): change password (needs the current password plus a fresh code; signs out every other session), generate new recovery codes (old ones stop working), and see or sign out active sessions.
- **Lost authenticator and recovery codes?** A person runs `docker compose exec imconnected node scripts/reset-2fa.mjs editor@example.org` (for the only active administrator who has no password it refuses, with a warning, unless `--yes-last-admin` is added, and then `node scripts/create-admin.mjs` is needed to sign in again) on the server, only after confirming the editor's identity out of band (for example by phone), and right before the editor signs in. In one transaction it deletes that user's authenticator, passkeys, recovery codes, linked Google and Microsoft accounts and sessions, and writes an `admin.reset_2fa` audit entry. The password stays; at the next sign-in the editor enrolls a new authenticator or passkey and gets new recovery codes. Administrators can do the same from **Editors** (see the [editor guide](EDITOR-GUIDE.md)), without server access.
